## §5. Escalations — PRE-TIERED per governance §4.1

### §5.1 CD-9.2a-E1 [Tier 1] · Model provenance discipline — attest SHA + license + source-origin

**Class:** honesty grammar (governance §1.1 · "class-with-claim" · "no fabricated values") + data-blind posture (governance §8) + client-promise (V1 outcome: "real owned material flows to qualified units").

**Question:** how do we attest the ASR + diarization models we run are the models we claim to run? Specifically: (a) SHA-pinning of model weights; (b) license-check per model; (c) source-origin attestation (the Owner requested "Whisper-class ASR" — but Whisper-class is a family, not a specific model).

**Authority-source language (BCR §3.1 V1-B3 verbatim):**

> A deterministic stub worker lands first and all guard gates prove against it before any GPU code exists (the established stub-first pattern). GPU perception models land behind the same worker interface.

**Promise-protected:** honesty grammar. A real ASR worker without pinned model provenance is a fabricated-claim risk — "we ran ASR" without evidence of which ASR at which weights. Downstream telemetry (V1-B4 `gpu_hours` + `unit_yield` per modality) attributes work to models; unlabeled attribution is fabricated.

**Options:**

- **α** — SHA-pin model weights + explicit license record + source-origin URL, all attested at test-time via a `services/perception/model_registry.py` module + `models_registry.v0.json` seeded EMPTY (data-blind § 8 · CI fixture-mode loads a minimal open-source ASR e.g. `openai/whisper-tiny` for CPU-mode green; 9.2b deployment loads production model per Owner topology decision).
- **β** — Log model name at runtime; no pinning. Softer; risks silent model swap.
- **γ** — No provenance at all; rely on packaging discipline (assumed model = actual model). Rejects honesty grammar.

**Recommended:** **α**. Rationale: (1) matches TF-E3 α + P8E-E7 α precedent (versioned registry over hard-coded values); (2) SHA-pinning is cheap (one JSON entry per model); (3) CI mode uses a light open-source model (whisper-tiny CPU-runnable) with public license, keeping data-blind + no-venue-assumption postures; (4) 9.2b will swap in production model weights per Owner ruling — the registry-bump pattern handles this cleanly (per §6.11-adjacent registration pattern from CD-E3 α).

**Escalation surface:** honesty grammar + frozen wire contract adjacency (models are effectively contracts). Full-rigor Tier-1. Owner ruling required BEFORE execution.

### §5.2 CD-9.2a-E2 [Tier 1] · CPU-mode vs GPU-mode execution — selection mechanism

**Class:** frozen wire contract adjacency (governance §1.1 last bullet) + security boundary indirect (worker code path leakage).

**Question:** by what mechanism is CPU-execution mode selected in CI vs GPU-execution mode at deployment? Runtime env var? Config flag? Compile-time constant? Adapter-seam-with-two-implementations?

**Authority-source language (Owner PART 2 verbatim):**

> CI posture, data-blind: synthetic/public-domain audio fixtures only; CPU-execution mode so the full test surface runs green without GPU hardware.

> GPU execution layer: model loading, VRAM management, audio batching, CUDA-container packaging — destination-agnostic (standard CUDA runtime, no venue assumptions; venue config is a 9.2b deployment fact).

**Promise-protected:** (i) frozen wire contract discipline — the mode selection MUST be evident at read-time, not implied by convention; (ii) security-adjacent — a GPU-only code path leaking into CPU-mode CI would silently expose paths that aren't proven green.

**Options:**

- **α** — Env var `PERCEPTION_EXECUTION_MODE={cpu,gpu}` read at module-import time inside `services/perception/gpu_execution/cuda_runtime.py`; module exports a `SELECTED_BACKEND` sentinel; both ASR + diarization workers dispatch through the sentinel. CI defaults to `cpu`; deployment sets `gpu`. Structural, single point of decision.
- **β** — Adapter-seam-with-two-implementations: `AsrCpuBackend` + `AsrGpuBackend`, chosen at worker-instantiation via constructor arg from a config file. More seams; more code; more evident.
- **γ** — Compile-time constant (e.g., `if CUDA_AVAILABLE: ...`). Runtime detection; risks silent swap when CUDA driver behaviour varies.

**Recommended:** **α**. Rationale: (1) single point of decision reads at import time — one place to audit; (2) env-var pattern matches prior discipline (MongoDB via MONGO_URL); (3) β doubles the module count without proportional audit-clarity gain; (4) γ makes the selected mode invisible in code (silent-swap risk).

**Escalation surface:** frozen wire contract shape (the selected-backend sentinel) + security path enumeration. Full-rigor Tier-1. Owner ruling required BEFORE execution.

### §5.3 CD-9.2a-E3 [Tier 1] · P9-E7 rider — "real perception under CPU-mode fixtures" semantics

**Class:** client-promise (governance §1.1 first bullet · V1 outcome) + honesty grammar.

**Question:** the P9-E7 rider verbatim says *"9.2's roster includes one cell re-asserting SM-G1 against real perception — the stub-proven loop closes at the natural moment."* Under CPU-mode CI (CD-9.2a-E2 α), what does "real perception" mean? Same output shape as stub? Or observably different (e.g., non-empty units[] for the audio fixture)?

**Authority-source language (Owner P9-E7 verbatim ratified 2026-07-08):**

> P9-E7 — SM-G1 proves against the stub; 9.3 closes independently; §4.1 baseline holds. The gate asserts pipeline mechanism — sample flows through intake, result grounds the envelope, marker renders — none of which depends on perception quality; quality is BM-V's job, and conflating them would make the console surface hostage to the RMS facts for zero mechanism-level gain. One rider: 9.2's roster includes one cell re-asserting SM-G1 against real perception — the stub-proven loop closes at the natural moment, same first-contact re-verification pattern as the conformance map.

**Promise-protected:** the rider closes an intentional first-contact re-verification loop. Its semantics must be evident to reviewers.

**Options:**

- **α** — "Real perception" = output shape identical to stub (matches stub interface), but observably non-degenerate: for a fixture audio containing spoken content, `units[]` is non-empty. Test asserts the wire-shape identity + non-empty units + grounding_marker renders. Loop closes on mechanism-level equivalence + real-model-produces-real-units.

- **γ** — "Real perception" = anything that isn't the stub module. Loosest reading; risks trivial re-branding of stub as "real" and passing.

**Recommended:** **α**. Rationale: (1) matches P9-E7 verbatim rationale (mechanism level, not quality); (2) non-empty-units assertion is a cheap real-perception discriminator (stub emits zero units by design); (3) β violates the "conflating them" prohibition explicitly.

**Escalation surface:** client-promise (SM-G1) + honesty grammar. Full-rigor Tier-1. Owner ruling required BEFORE execution.

### §5.4 CD-9.2a-E4 [Tier 1] · Purge-attestation AST gate — mechanism for real media paths

**Class:** frozen wire contract discipline (V1-D1 raw-never-persists never-rule) + honesty grammar.

**Question:** V1-D1 says *"Raw AV exists worker-side transiently only and is purged on job completion with attestation recorded in the job result."* At the stub, this is a trivial constant. At real workers reading real audio bytes, how do we STRUCTURALLY prove no long-lived raw audio reference exists after purge_attestation is set?

**Authority-source language (BCR §3.1 V1-D1 verbatim):**

> V1-D1  Raw AV exists worker-side transiently only and is purged on job completion with attestation recorded in the job result. The system keeps reextraction_handles (pointers), never long-term raw copies.

**Authority-source language (Owner PART 2 verbatim):**

> purge attestation on real media paths.

**Promise-protected:** never-rule V1-D1 (governance §1.1 first bullet: client-promise-adjacent · raw-never-egresses). A real worker holding a long-lived reference to audio bytes (module-level cache, class attribute, closure capture) IS the never-rule violation. Structural proof required; convention insufficient.

**Options:**

- **α** — AST/reflection gate (§6.10 class) over `services/perception/asr_worker.py` + `diarization_worker.py` + `gpu_execution/*.py`: (i) grep-negative on `self.raw_audio =` / class-level `_audio_cache = ` / module-level `AUDIO_BYTES = ` pattern; (ii) walker asserting audio bytes are held only inside function scopes that terminate with a `purge_attestation` call before return. Whitelist for legitimate patterns.
- **β** — Runtime assertion via context manager (`with AudioBytes(handle) as bytes: ... assert bytes.purged`). Runtime; risks bypass.
- **γ** — Convention (comment + code review). Rejects mechanical enforcement per V1-H2 verbatim: *"The never-rules are enforced mechanically, not conventionally: grep/AST gates prove no ledger-write call sites and no transform-key access in worker code."*

**Recommended:** **α**. Rationale: (1) V1-H2 mandates mechanical enforcement; (2) matches AS-G6 + TF-G9 + CD-G3 precedent (§6.10 rate class); (3) whitelist-and-walker pattern is established; (4) β adds runtime overhead per audio byte load without structural certainty; (5) γ rejected by V1-H2.

**Escalation surface:** frozen wire contract shape (V1-D1 never-rule) + honesty grammar. Full-rigor Tier-1. Owner ruling required BEFORE execution.
