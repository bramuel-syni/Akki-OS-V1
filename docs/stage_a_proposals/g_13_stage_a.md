### §5.1 · E1 · Worker context-harnessing prompt-block format · **Tier-1** (Standing Rule v3 impact varies by option)

**Surface:** Registry Doctrine §6.2 verbatim: *"every model worker receives the promises in force on its task — mandate, promise, and service trace for the functions it touches — as part of its operating prompt"*. The MANDATE (mandate + promise + service_trace triplet for every in-scope function) is specified verbatim; the FORMAT (how the triplet block is serialized inside the operating prompt) is builder-open with 3 postures.

**Builder analysis (does NOT resolve):** 3 structurally distinct posture options; Owner rules.

**Owner ruling surface:**

- **(a) Structured YAML block** (frontmatter-like YAML block prepended to the operating prompt · one key per Registry field · one list-item per in-scope function):
  - Byte-level: `context_block: List[RegistryContextRow]` where `RegistryContextRow(function_id: str, mandate: str, promise: str, service_trace: List[str])`. Serialized as YAML block delimited by `---` markers before the operating-prompt body.
  - Parity impact: **NEW frozen contract** `RegistryContextRow@v0` at `backend/contracts/registry_context_row_v0.py` · Parity 33→34 seal at execution atomic.
  - **Standing Rule v3 impact: PRESERVED** — new contract lands additive (v0-first-issue) per `PROM-S1-additive-versioning`. The 33 prior contracts remain byte-identical.
  - Trade-off: heaviest ceremony (Parity seal event); cleanest machine-readability; highest LLM-parseability per structured-context best-practice.
  - Precedent alignment: matches EAB-3 (a1) single-contract landing pattern.

- **(b) Annotated markdown block** (markdown block with `### Function: <id>` sub-headers · `**Mandate:**` / `**Promise:**` / `**Service trace:**` labels):
  - Byte-level: constructed as string via prompt-builder function at `backend/services/registry_context/prompt_builder.py`; no frozen contract; format template hardcoded in service.
  - Parity impact: **NO SEAL** (no contract touch · pure service-layer serialization).
  - Standing Rule v3 impact: PRESERVED (no contract touch).
  - Trade-off: lighter ceremony; markdown is human-readable AND LLM-parseable at rung-3/rung-4; slight structural ambiguity vs YAML.
  - Precedent alignment: matches AF-E3 α service-layer-only telemetry pattern (no contract touch).

- **(c) Structured JSON block embedded in prompt** (JSON object `{"context": [...]}` embedded literally in prompt):
  - Byte-level: constructed as JSON string via prompt-builder; format template hardcoded in service.
  - Parity impact: NO SEAL (no contract touch).
  - **Standing Rule v3 impact: PRESERVED** (no contract touch) BUT JSON-in-prompt has known LLM-parsing brittleness at rung-3/rung-4 (per general open art) — WOULD VIOLATE the "worker errs toward the promise" discipline of §6.2 if the JSON's structural syntax competes for LLM attention with the mandate content.
  - Trade-off: none live at pre-name — inferior to (a) on machine-readability AND inferior to (b) on rung-3/rung-4 parseability.
